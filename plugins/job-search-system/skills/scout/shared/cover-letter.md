# Cover letters: how to draft, revise and review one

`writing-rules.md` says what a letter may claim and how it is laid out.
This file says how to make it good. It applies to the cover letter in draft
mode, to a user's request to revise one, and to the reviewer's read
(decision 026). Where this file and `voice.md` or an employer's instructions
disagree, they win.

## What a letter is for

A resume lists what the user did. A letter makes a case the resume cannot
make alone: what this employer needs most, the one or two things the user
did that show it, and how they connect. If a sentence repeats a resume
bullet without adding why it matters here, cut it or make it a story.

A letter that could be sent unchanged to a competitor is not finished.

## Inputs and what counts as evidence

- The full posting, `facts.md`, `stories.md`, `answers.md`, `voice.md` and
  the situation fields in `profile.yaml`.
- Evidence is a `[confirmed]` fact, or a story whose fact IDs are all
  confirmed. An old draft, an earlier letter or the drafter's own text is
  never evidence. Reuse wording from an old letter only if each claim in it
  traces to a confirmed fact again.
- A reason for wanting the role comes only from `answers.md`, `wants.md` or
  what the user said in this session. Never infer motivation from the
  user's background, and never write enthusiasm for an employer the user
  has not expressed. Without a stated reason, ground interest in the work
  itself, as the posting describes it.
- Company facts come from the posting or the employer's own pages. Research
  only if it would materially strengthen the letter and the user has not
  said not to.

## Steps

1. **Find what the employer needs most.** From the posting, the two or three
   responsibilities that explain why the role is open, split into required
   and preferred. Use the employer's words where they describe the user's
   work accurately.
2. **Choose one or two examples.** Not a career summary. Prefer a story in
   `stories.md`; otherwise build one from confirmed facts. For each example
   note what the user personally did, the confirmed outcome or scope, and
   why it matters for this job. Use a number only if a confirmed fact has
   it. With no number, name a concrete deliverable or scope instead. Do not
   turn a team result into a personal one, and do not raise scope.
3. **Choose one angle** from the table below.
4. **Tell the examples as stories.** See "Telling the example" below.
5. **Write the letter** (shape and length below).
6. **Read it as a skeptical hiring manager.** Competitor test. Does it add
   something the resume does not? Does every claim trace? Is the closing
   plain? Does the opening say the role and a specific reason? Fix, or move
   the issue to the notes.

## Angles

| Application | Strong angle, when the facts support it | Avoid |
| --- | --- | --- |
| Engineering or people manager | One example of developing people or helping a team deliver under a real constraint, and how the user led it | Listing every team managed; turning a team result into a personal claim; a philosophy with no example |
| Manager to hands-on technical role | One example of individual technical work, and the user's own reason for wanting to build again | Apologizing for managing; claiming recent hands-on work the facts do not show |
| Hands-on software or IT role | Lead with what the user personally built or troubleshot, dated honestly, and what is recent | Letting old work read as current; calling an old or lapsed credential active |
| Return to a field after time away | The most relevant earlier work, accurately dated, plus recent evidence that carries over | Burying a material gap in vague words |
| Career change or industry change | A familiar problem in the new domain, in the employer's terms, then the user's stated reason for the move | Claiming domain expertise or mission fit the user has not established |
| Lower title than the user's last | What draws the user to the day-to-day work, only if `answers.md` or the user says so | Calling the user overqualified; framing the job as a fallback; sounding defensive |

If the user is changing careers, follow the situation rules in
`writing-rules.md`. State the move plainly, bridge it with confirmed
facts, use only a reason the user has given, and do not apologize.

A gap needs explaining only if `situation.gap.explanation` says so. State it
once, in the user's words, and go on to evidence.

If the posting requires something the facts do not show (a degree, an active
certification, a language, a tool), do not imply the user has it. Say what
the user does have, once, and put the gap in the notes for the user. Never
hide it in vague words.

## Telling the example

An example is a short story, not two facts set side by side. Each one
answers four things, in plain sentences:

1. What was going on, and why it mattered.
2. What the user did, in the first person, specifically.
3. What changed, using only confirmed outcomes.
4. Why that matters for this role: one sentence in the posting's terms.

Do not leave two facts next to each other and let the reader guess how they
relate. If a trained coach is said to have worked with a CTO, the letter
must say what the coaching approach was in that moment, or not draw the
line at all. A sentence that links facts may interpret them; it may not add
a fact.

Sentences that interpret, motivate or connect need no fact ID. Everything
factual in the story does, in the claim map.

## Shape and length

- Open with the role and a specific reason for interest or fit, in the
  user's voice. No canned opening.
- Two short middle paragraphs, one example each, or one longer paragraph if
  the user has only one strong story. Each example gets enough room to
  tell it (see the steps above).
- End with one or two plain sentences about how the user would help: add
  value, support the team, help it deliver. Do not ask for a conversation
  about how the user would run something, and do not demand a reply. A
  simple "I'd like to talk" is fine only if `voice.md` says that is how the
  user writes.
- Length: `voice.md` sets it. With no setting, 250 to 350 words of body text,
  and never more than one page. Shorter reads as thin and longer is
  rarely read. An employer's instruction (a word limit, a portal field,
  specific questions) overrides every default here. Match a portal field's
  length and leave out the postal block.
- Greeting and sign-off follow `writing-rules.md`.

## Voice

Read `voice.md` first. Use its samples to hear the writer, never to take
claims. Default when `voice.md` is silent: plainspoken, warm, direct and
quietly confident, with active verbs and ordinary words. No generic praise,
no keyword stuffing, no "perfect fit", no inflated impact, and no phrase on
the banned list.

## What the user gets back

- **Draft or revise:** the clean letter, ready to use. No citations, notes
  or placeholders inside it.
- **Before sending:** separately, at most three specific things the user
  needs to check or decide (a missing requirement, a story that needs
  detail, a claim worth verifying). Put them in the plan's "What is thin"
  section and in the user message. Say nothing if there is nothing.
- Nothing is sent, submitted or filled in.

## Revising an existing letter

Keep the user's own wording and voice. Change only what the request or a
blocker calls for. If the user's edit adds a claim, check it against
`facts.md` and say if it does not trace. A copy edit never needs the
posting. A new tailored letter does: without the full posting, ask for it
once; do not call a letter tailored when the posting was not read.

## Reviewing a letter only

When the user asks what is weak and does not ask for a rewrite, give up to
three prioritized issues, each with a concrete edit. Do not rewrite the
whole letter. Lead with the issue that most changes the case: a story that
does not connect, a claim that does not trace, a closing that asks for too
much, a gap left unstated, or a sentence that any applicant could write.
